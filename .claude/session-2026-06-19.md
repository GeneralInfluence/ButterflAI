### What we designed and built

#### Agent-to-agent desire coordination protocol
Full system for users to express weekly desires (e.g. "work out twice, go out with a friend or two, one chill night"), have agents coordinate with each other autonomously, and surface minimal prompts to users.

**Files created/modified (all committed to main):**
- `web/mcp-messages.js` — builder functions + outbound validator for two protocol classes:
  - **Coordination** (explicit scheduling): `buildProbe`, `buildInterest`, `buildAvailability`, `buildProposal`, `buildConfirm`, `buildCounter`, `buildReject`, `buildCancel`
  - **Ambient** (soft social signals): `buildAmbientIntent`, `buildAmbientCancel`
  - Outbound validator strips unlisted fields, blocks free-text strings, validates all values are enums/IDs/dates
- `web/coordination.js` — full session state machine (initiator + responder roles), window intersection logic, ambient signal store/query
- `web/desires.js` — LLM parsing of free-text desires → structured records; sanitizer; vague candidate strategies; one-off vs recurring horizons; hard delete with receipt; `raw_text` zeroed immediately after parsing
- `web/coord-loop.js` — ticks every 5 min: pending desires → resolve candidates → `createSession` + `startProbing`; recurring templates; escalation notify
- `web/db/migrations/003_coordination.sql` — desires, coord_desires VIEW, coordination_sessions, coord_session_peers, ambient_signals tables
- `web/db/migrations/004_desires_v2.sql` — candidate_strategy, recurrence, horizon, raw_text_zeroed fields
- `web/db/migrations/005_agent_endpoint.sql` — agent_endpoint column on users
- `COORDINATION_PLAN.md` — full protocol spec, message schemas, state machine, open questions
- `LAUNCH_CHECKLIST.md` — 8-section pre-launch checklist: security, infra, testing, legal, observability, KMS steps, per-user SQLite migration steps, sign-off gate

**Agent tools added:**
- `parse_desires` — parses free-text desire statement, stores structured records, returns summary
- `delete_desires` — hard delete with cancel of in-flight coord sessions, receipt
- `whats_happening` — aggregates ambient signals + venue lookup (identity severed: venues from lookup, not broadcast)

#### Key privacy decisions locked
- `raw_text` zeroed immediately after parsing — most sensitive field never persists
- `coord_desires` VIEW excludes `raw_text` — coordination layer structurally cannot see it
- LLM never constructs outbound agent-to-agent messages — only parses inbound desires
- All outbound coord messages are deterministic code through typed builders
- No free-text fields in any agent-to-agent message type
- Reject/cancel carry empty payloads — reasons stay private
- Ambient signals carry: category + neighborhood + period + certainty — no venue, no names, no group size
- Venue suggestions in "what's happening" come from venue lookup, not from broadcast (identity severed)

#### Wallet encryption for desires — re-evaluated and still deprecated
Same problem as the NFT approach: agent must act autonomously over SMS without user's device online. Wallet decryption requires live wallet signature → breaks agent autonomy. Delegated session key recreates the "server holds the key" situation. Wallet role unchanged: identity + future social budget only.

#### Database architecture question
Single SQLite DB currently (`/data/butterflai.sqlite`). Discussed per-user SQLite split (`main.sqlite` + `users/{user_id}.sqlite`) as pre-launch task — physical isolation, a bug in one user's session cannot touch another's file. Documented in LAUNCH_CHECKLIST.md §7 with detailed migration steps.
